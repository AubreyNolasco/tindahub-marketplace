Found and fixed two pre-existing gaps (neither introduced by the promotion-system work), left one flagged for a business-policy decision rather than silently changed, per `BUSINESS_RULES.md`'s non-destructive policy:

A merchant could set `status='completed'` directly, skipping `complete_referral_appointment()`'s wallet debit/credit entirely — marking a referral fulfilled without ever paying the reseller the `referral_fee` they were owed. Grepped the whole frontend first: zero direct `.from('referral_appointments')` calls exist anywhere, so `revoke insert, update, delete on public.referral_appointments from authenticated` (migration `20260807000400`) breaks nothing.

Not changed.
  - **Methodology correction, found while trying to verify the `referral_appointments` fix more rigorously afterward:** attempted to confirm "a direct update is now rejected" by running one via `supabase db query --linked` with `request.jwt.claims` set to simulate a specific user — and it **succeeded**, despite the grant genuinely being revoked (re-confirmed via `information_schema.table_privileges` right after — still gone). Root cause: `supabase db query`'s connection is a superuser/table-owner-equivalent role, which bypasses RLS and table grants entirely regardless of what `request.jwt.claims` is set to — that GUC only changes what `auth.uid()` returns to PL/pgSQL code, it does not change *which Postgres role is actually executing the query*. So this technique is only a valid test for **application-level checks** (a `RAISE EXCEPTION` inside a `SECURITY DEFINER` function body reading `auth.uid()`/`is_admin()`, like `create_voucher`'s `FORBIDDEN` or `delete_voucher`'s `VOUCHER_HAS_REDEMPTIONS`) — it can never demonstrate that an RLS policy or a `GRANT`/`REVOKE` is actually enforced, since this connection is never subject to either. Checked back through this session's other "verified live" claims: none of them actually claimed an RLS/grant rejection was tested this way (the grant claims were always via the `information_schema` catalog check, which *is* reliable regardless of connecting role) — so nothing already written down needs retracting, but the distinction matters enough to write down so a future session doesn't reach for this technique to "prove" an RLS fix and trust a false negative. The only way to *actually* test RLS/grant enforcement end-to-end is a real authenticated PostgREST/browser session — which is exactly the capability blocked in this environment by the device-approval issue noted elsewhere in this file and in `TASK6.md`.
