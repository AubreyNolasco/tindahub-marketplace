Architecture review · tindahub-marketplace

A Delivery Provider Engine for a stack that already exists

The brief asked for a Laravel service layer. This repo runs React on Supabase — Postgres, RPCs, and Deno edge functions. Below is the same engine, translated to that stack, with the parts of the brief I'd push back on called out explicitly rather than quietly implemented.

Stack: Postgres · Deno edge functions · React/Vite Scope: 1 real integration today (Lalamove) → N

00Verdict

The core idea is right: a provider-agnostic engine with ownership tiers, priority, and fallback. Build it. But three parts of the brief as written would produce something worse than what you have today if implemented literally:

your two flowcharts (own-vs-reseller, admin-vs-subscription) are actually one priority chain, not two independent trees; "automatic selection + retry" pushes toward a synchronous multi-provider loop inside a user-facing request, which is a timeout risk against real courier APIs; and twelve deliverables shipped at once is a quarter of work disguised as a sprint, which cuts against your own "keep it simple" constraint. The design below keeps the ambition and fixes those three.

01Current system, reviewed

Confirmed directly in the codebase, not assumed:

  • delivery_provider on orders is free text — a merchant types "Lalamove, J&T, Grab" by hand in DeliveryModal.jsx. No FK, no validation, no analytics possible on which provider actually moved a package.
  • Lalamove is the only real integration, and it's wired directly into the shipping-fee flow via a courier-specific column (orders.lalamove_quote_id). A second courier means duplicating lalamove-quote/lalamove-book near-from-scratch, not implementing an interface.
  • Ownership only exists at the reseller tier — lalamove_settings.owner_id. There is no merchant-owned or platform-owned courier account anywhere. The exact chain your flowchart describes (own → reseller → admin+subscription) has zero supporting code today.
  • No retry, no fallback, no logging. A failed quote throws LALAMOVE_NOT_CONNECTED and stops. There is no concept of "try the next provider."

02Where the brief needs pushback

Pushback 1 — your two flowcharts are one chain

The diagram you sent earlier (own API → reseller API) and the admin/subscription diagram in this brief aren't two separate decisions — they're three rungs of the same ladder: Merchant-owned → Reseller-owned → Platform-owned (subscription-gated). Modeling them as one ordered candidate list, rather than two branching trees, is simpler to implement, simpler to reason about, and lets you add a fourth tier later without restructuring anything.

Pushback 2 — "automatic selection + retry" implies async, not a bigger loop

Real courier APIs are slow (1–5s+) and occasionally down. Looping through five of them synchronously inside one edge-function invocation risks timing out the merchant's browser request. This repo already has the right pattern for this — notify_lalamove_dispatch_ready is a DB trigger that fires an edge function asynchronously after a quote is accepted. Reuse it: the first attempt is synchronous (matches current UX, fast path), and fallback-to-next-provider on failure runs async via the same trigger mechanism, not a longer synchronous loop.

Pushback 3 — twelve deliverables now vs. "keep it simple"

Provider registration, config, ownership, priority, auto-selection, manual selection, fallback, retry, logging, quote, booking, tracking, cancellation — built simultaneously — is the definition of unnecessary complexity for a system with one live integration today. Phase it (§10): ship the adapter interface with Lalamove as the only adapter first, so the abstraction gets proven against a real integration before a second and third provider are added, and before auto-selection has anything to select between.

Pushback 4 — is "Merchant Delivery API" real demand yet?

Nothing in the current data model suggests merchants run their own delivery fleets — today merchants pack and hand off, resellers own the courier relationship and the end customer. Build the merchant ownership slot in the schema (it's free — same table, one enum value), but don't build onboarding UI for it until a merchant actually asks. Speculative UI is the expensive kind of speculative.

03Target architecture

Four layers, matching what's already idiomatic in this repo — no new frameworks, no service-layer reinvention beyond what the engine itself needs:

  • Catalog & config (Postgres) — what providers exist, who has an account with which one, at what priority. Source of truth, RLS-protected.
  • Selection (Postgres RPC, security definer) — given an order, returns the ranked candidate list. Pure read, no side effects, cheap to call from anywhere.
  • Adapters (Deno edge functions, shared module) — one small file per courier implementing a fixed interface: quote, book, track, cancel. This is the extension point; adding a provider never touches the selector or the UI.
  • Orchestration (edge functions + DB trigger) — synchronous first attempt for UX; async trigger-driven fallback for resilience, reusing the pattern already proven by Lalamove auto-dispatch.

07Database schema

Follows the conventions already established in this repo's migrations: RLS enabled immediately on every new table, privileged RPCs as security definer with a pinned search_path, secrets never stored as plain columns, and a trailing notify pgrst to reload the schema cache.

supabase/migrations/20260801000100_delivery_provider_engine.sqlsql
-- 1. Catalog of known provider types — extensible without touching code
create table public.delivery_providers (
  code text primary key,            -- 'lalamove' | 'grabexpress' | 'borzo' | 'ninjavan' | 'jnt' | 'manual'
  name text not null,
  supports_tracking boolean not null default true,
  supports_cancellation boolean not null default true,
  is_active boolean not null default true,   -- platform kill-switch, per provider
  created_at timestamptz not null default now()
);
alter table public.delivery_providers enable row level security;
create policy "providers are publicly readable"
  on public.delivery_providers for select using (true);
create policy "only admin can modify providers"
  on public.delivery_providers for all using (public.is_admin());

-- 2. Who has a configured account with which provider (replaces lalamove_settings)
create type public.delivery_owner_type as enum ('merchant', 'reseller', 'platform');

create table public.delivery_provider_accounts (
  id uuid primary key default gen_random_uuid(),
  owner_type public.delivery_owner_type not null,
  owner_id uuid,                     -- null only when owner_type = 'platform'
  provider_code text not null references public.delivery_providers(code),
  is_enabled boolean not null default true,
  priority int not null default 100, -- lower tried first, within the same owner_type
  credentials_id uuid,               -- pointer into vault; never a raw secret column
  metadata jsonb not null default '{}',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint owner_id_required_unless_platform
    check (owner_type = 'platform' or owner_id is not null),
  unique (owner_type, owner_id, provider_code)
);
alter table public.delivery_provider_accounts enable row level security;
create policy "owners manage their own accounts"
  on public.delivery_provider_accounts for all
  using (owner_id = auth.uid() or public.is_admin());

-- 3. One row per booking attempt lifecycle (replaces ad hoc columns on orders)
create table public.delivery_bookings (
  id uuid primary key default gen_random_uuid(),
  order_id uuid not null references public.orders(id),
  provider_account_id uuid references public.delivery_provider_accounts(id),
  provider_code text not null,
  status text not null default 'quoted',  -- quoted|booked|in_transit|delivered|cancelled|failed
  external_quote_id text,
  external_order_id text,
  tracking_number text,
  fee numeric(10,2),
  idempotency_key text not null unique,   -- order_id + attempt — blocks double-booking on retry
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
alter table public.delivery_bookings enable row level security;
create policy "participants can view their bookings"
  on public.delivery_bookings for select
  using (
    exists (select 1 from public.orders o where o.id = order_id
            and (o.merchant_id = auth.uid() or o.reseller_id = auth.uid()))
    or public.is_admin()
  );

-- 4. Structured audit log per attempt (quote | book | track | cancel)
create table public.delivery_provider_logs (
  id bigint generated always as identity primary key,
  order_id uuid references public.orders(id),
  booking_id uuid references public.delivery_bookings(id),
  provider_code text not null,
  action text not null,
  ok boolean not null,
  request jsonb,
  response jsonb,
  error text,
  created_at timestamptz not null default now()
);
alter table public.delivery_provider_logs enable row level security;
create policy "admin can read logs"
  on public.delivery_provider_logs for select using (public.is_admin());

-- 5. Selection RPC — ranked candidates for an order, service_role only
create or replace function public.resolve_delivery_candidates(p_order_id uuid)
returns setof public.delivery_provider_accounts
language sql security definer set search_path = public as $$
  select dpa.*
  from public.delivery_provider_accounts dpa
  join public.delivery_providers dp on dp.code = dpa.provider_code and dp.is_active
  join public.orders o on o.id = p_order_id
  where dpa.is_enabled
    and (
      (dpa.owner_type = 'merchant' and dpa.owner_id = o.merchant_id) or
      (dpa.owner_type = 'reseller' and dpa.owner_id = o.reseller_id) or
      (dpa.owner_type = 'platform' and exists (
         select 1 from public.subscriptions s
         where s.owner_id = o.reseller_id and s.status = 'active'
      ))
    )
  order by
    case dpa.owner_type when 'merchant' then 1 when 'reseller' then 2 else 3 end,
    dpa.priority asc;
$$;
revoke all on function public.resolve_delivery_candidates(uuid) from public, anon, authenticated;
grant execute on function public.resolve_delivery_candidates(uuid) to service_role;

notify pgrst, 'reload schema';

Backward compatibility: keep orders.delivery_provider as a denormalized display column, synced from delivery_bookings.provider_code on write. Existing reporting/UI that reads it keeps working untouched.

09Interfaces & adapters

The extension point. Everything above exists to keep this interface the only thing a new provider has to implement.

  ok: boolean;
  externalQuoteId?: string;
  fee?: number;
  currency?: string;
  etaMinutes?: number;
  error?: { code: string; message: string; retryable: boolean };
}

  ok: boolean;
  externalOrderId?: string;
  trackingNumber?: string;
  error?: { code: string; message: string; retryable: boolean };
}

export interface DeliveryProviderAdapter {
  code: string;
  getQuote(input: QuoteInput, credentials: unknown): Promise<QuoteResult>;
  createBooking(input: BookingInput, credentials: unknown): Promise<BookingResult>;
  getTracking(externalOrderId: string, credentials: unknown): Promise<TrackingResult>;
  cancelBooking(externalOrderId: string, credentials: unknown): Promise<CancelResult>;
}
supabase/functions/_shared/delivery/registry.tsts
import { lalamoveAdapter } from "./adapters/lalamove.ts";
import { manualAdapter } from "./adapters/manual.ts";
// grabexpress / borzo / ninjavan / jnt slot in here as they ship — nothing else changes

const registry = new Map<string, DeliveryProviderAdapter>([
  [lalamoveAdapter.code, lalamoveAdapter],
  [manualAdapter.code, manualAdapter],
]);

export function getAdapter(code: string): DeliveryProviderAdapter {
  const adapter = registry.get(code);
  if (!adapter) throw new Error(`No adapter registered for provider "${code}"`);
  return adapter;
}
supabase/functions/_shared/delivery/selector.tsts
const MAX_RETRIES = 2;

export async function selectAndQuote(candidates: ProviderAccount[], order: Order) {
  for (const candidate of candidates) {
    const adapter = getAdapter(candidate.provider_code);
    const creds = await loadCredentials(candidate.credentials_id);
    let attempt = 0;
    while (attempt <= MAX_RETRIES) {
      const result = await adapter.getQuote(toQuoteInput(order), creds);
      await logAttempt(order.id, candidate, "quote", result);
      if (result.ok) return { candidate, result };
      if (!result.error?.retryable) break;   // business error → next provider, no retry
      attempt++;
      await backoff(attempt);
    }
  }
  return null; // exhausted → caller falls back to manual / standard delivery
}

manual.ts is worth calling out: it implements the same interface but its getQuote/createBooking just echo back whatever the merchant typed, with ok: true. That's what lets "standard delivery" be the last candidate in the same list instead of a special case the selector has to know about.

10Migration plan — six phases, each independently shippable

Strangler-fig, not a rewrite. Every phase leaves the system in a fully working state; nothing waits for phase 6 to be useful.

Phase 0 · Catalog only

Seed, don't switch anything over

Create delivery_providers, seed six rows (five couriers + manual). Nothing reads it yet. Zero behavior change.

Phase 1 · Wrap Lalamove

Refactor, not rewrite

Move the existing Lalamove logic behind the adapter interface. lalamove-quote/lalamove-book keep their exact external request/response shape. Proves the interface against a real integration before a second provider exists.

Phase 2 · Formalize ownership

Migrate reseller accounts

Create delivery_provider_accounts, backfill from lalamove_settings (owner_type='reseller'). Keep lalamove_settings as a read-only compatibility view for one release, then drop it.

Phase 3 · Replace the free-text field

DeliveryModal switches over

Add delivery_bookings. Backfill orders.delivery_provider text into it by matching against the catalog — unmatched values fall to manual, original text preserved in metadata. Swap the free-text input for DeliveryProviderSelector.jsx.

Phase 4 · Add real adapters, one at a time

GrabExpress, then Borzo, Ninja Van, J&T

Each ships behind its own is_active flag on delivery_providers, so a broken sandbox integration can't reach production traffic. Each gets its own contract tests before is_active = true.

Phase 5 · Selection engine goes live

Auto-selection, fallback, retry

resolve_delivery_candidates + selector.ts + the async fallback trigger, rolled out per-reseller behind a feature flag so it's reversible if something misbehaves against real traffic.

Phase 6 · Platform tier + observability

The part your flowchart was actually describing

Platform-owned account, subscription gating, delivery_provider_logs dashboard for admin, and a circuit breaker that auto-disables a flapping provider.

12Best practices

  • Idempotency keys on every booking call — non-negotiable once retry exists.
  • Vault-only secrets, one pattern for all five providers — this repo already has it, don't invent a second one.
  • security definer with a pinned search_path on every privileged RPC, matching the existing migration convention.
  • Circuit breaker per provider — auto-disable after N consecutive failures, alert admin, don't wait for a human to notice.
  • Structured logs keyed by order_id so a support ticket becomes one query, not five.
  • Feature-flag the rollout per reseller — auto-selection is new failure surface against real money movement.
  • Don't build a workflow/saga engine. An ordered candidate list plus one DB trigger is enough at current order volume. Revisit only if volume or provider count actually outgrow it — not before.
