# Automatic Distance-Based Shipping Fee, PSGC+Leaflet-Only Address System — Progress & Handoff

**Status: built, migrated to production (commits `b8f01ce`/`7bc008c`/`<this fix>` on `agent/fix-address-map-sync`, migrations applied via `supabase db push` and spot-verified with live RPC calls), NOT yet click-tested in a browser. Gap 1 (dispatch blocked for automatic orders) is now fixed — see "Gap 1 — FIXED" below. Gap 2 (Lalamove vehicle-type selection) is still open.**

Full architectural audit + rationale (why each decision was made, what was rejected and why) is a published artifact the owner already has: ask them for the link if it's not in your context, or re-derive from this file — this doc is the code-accurate summary, that one is the reasoning.

## Original request

Owner wanted the address/map/shipping/checkout system redesigned so PSGC (Philippine Standard Geographic Code) is the authoritative address hierarchy, a map lets the customer confirm an exact delivery pin, and shipping fee is calculated automatically and shown *before* the order is placed — inspired by Lalamove's distance-based pricing but not copying it, admin-configurable, with the backend as the sole source of truth (never trust a client-sent fee).

Two scope-defining decisions the owner gave mid-session, both **final, do not re-litigate without asking**:
1. **No merchant-proposed shipping fee as the default path.** Automatic, distance-based, shown to both reseller and merchant — the old "merchant proposes a fee after the order exists, reseller accepts/declines" flow is a *fallback only*, not the normal case.
2. **No external APIs at all — PSGC + Leaflet only.** No LocationIQ, no Nominatim, no OSRM, no Google Maps/Routes. Distance is straight-line (haversine) between two map pins × a configurable multiplier, not real road distance. This was a hard reversal of an earlier draft that recommended self-hosting OSRM — the owner explicitly rejected adding any new hosted service or API key.

## What was built

### Database (5 new tracked migrations, `supabase/migrations/`, all applied to the live project `ttscpfsodrcyllyvvqzb`)

- **`20260813000100_shipping_engine_tracked_migration.sql`** — moved the still-live parts of `supabase/shipping_engine_migration.sql` (an *untracked* file outside the numbered migration sequence — the same pattern that broke `quote_order()` once in production before, per `20260723000900_quote_order_self_contained_pricing.sql`'s own comment) into a real tracked migration: `shipping_settings` table, `calculate_standard_shipping()`, the `require_complete_customer_address`/`save_signup_address` triggers, and the columns they all depend on. Dropped four confirmed-dead RPCs (`place_standard_order`, `place_customer_standard_order`, `place_mapped_order`, `place_customer_mapped_order` — nothing in `src/` ever called them, only `place_receiver_shipping_order`/`place_customer_receiver_shipping_order` and `calculate_standard_shipping` directly are used) and the unused `shipping_distance_quotes` table. `supabase/shipping_engine_migration.sql` and `supabase/test_account_auth_setup.sql` got a "SUPERSEDED — do not run this file again" header rather than being deleted, to preserve history.
- **`20260813000200_shipping_pricing_engine.sql`** — `haversine_km(lat1,lng1,lat2,lng2)` (pure SQL, `immutable`, no external call). `shipping_pricing_rules` table: versioned/effective-dated config mirroring the existing `system_policies` precedent (draft → published → archived, one published row per `vehicle_type` enforced by a partial unique index, transitioned through `publish_shipping_pricing_rule(target_id)` not a plain UPDATE). Seeded with today's exact rate structure as v1/published for both `motorcycle` (₱49 base, 5km included, ₱6/km, ₱5/km beyond) and `sedan` (₱100 base, ₱18/km, ₱15/km beyond) — both `rounding_increment=5`, `road_directness_multiplier=1.3`. Rewrote `calculate_standard_shipping()` to read these instead of hardcoded literals; vehicle-selection logic (weight/dimension thresholds, special-handling detection) is unchanged. The function's return jsonb now includes `'rule_id'` so callers don't need a second lookup.
- **`20260813000300_remove_locationiq_integration.sql`** — deletes the now-dead `integration_configs` row for `maps.locationiq`.
- **`20260813000400_automatic_shipping_checkout.sql`** — the core of this work. `orders` gets `shipping_pricing_rule_id` and `shipping_fee_breakdown jsonb`. `quote_order()` and `place_order()` both **dropped their `p_shipping_fee` parameter entirely** — they now take `p_delivery_latitude`/`p_delivery_longitude` instead, which carry no financial meaning by themselves. Inside `place_order()`: looks up the merchant's `pickup_latitude`/`pickup_longitude`, and if both pins exist (and the delivery coordinates pass a rough PH bounding-box check, lat 4–21 / lng 116–127), computes `haversine_km(...)` then calls `calculate_standard_shipping()` inside a `begin/exception when others` block. **On success**: `shipping_fee` = the real computed fee, `shipping_payment_method = 'prepaid_wallet'`, `shipping_payment_status = 'paid'`, and it's folded into the same wallet debit as subtotal + processing fee, in the same transaction. **On any failure** (no pin, `MISSING_PACKAGE_INFORMATION`, `MANUAL_QUOTATION_REQUIRED`, anything) — falls back to exactly today's pre-existing behavior: `shipping_fee = 0`, `shipping_payment_method = 'receiver_pays_on_delivery'`, and `propose_order_shipping_fee`/`respond_order_shipping_fee` (untouched by this migration, still in `20260722000900_shipping_fee_confirmation.sql`) remain available as the manual override path. Checkout never hard-fails just because automatic pricing wasn't possible for a given cart. `place_receiver_shipping_order()` no longer forces `shipping_fee back to 0` after calling `place_order()` (it used to, unconditionally — that line is gone). `place_customer_receiver_shipping_order()` (order-for-a-saved-customer path) pulls the customer's own saved `latitude`/`longitude` server-side rather than trusting anything from the client, consistent with how it already re-validates the customer's address.
- **`20260813000500_barangay_codes.sql`** — `barangay_code text references psgc_barangays(code)` added to `profiles`, `merchant_profiles`, `customers`. Province/city already had code columns (`psgc_provinces`/`psgc_cities`); barangay was name-only before this.

## Known gaps — read before continuing

### Gap 1 — FIXED: dispatch was blocked for automatically-priced orders

`set_order_delivery()` (was `20260723001900_fix_database_lint_warnings.sql:5-49`) — the RPC `DeliveryModal.jsx` calls to mark an order `shipped` and record courier/tracking info — required `shipping_fee_confirmation_status='accepted' and proposed_shipping_fee is not null`, a pair **only ever set by the manual negotiation flow**. The automatic path (`shipping_payment_method = 'prepaid_wallet'`) never touched those columns, so they stayed `null` — a merchant had no way to mark an automatically-priced order as shipped through any existing UI. Same condition also gated the `enforce_shipping_fee_before_dispatch()` trigger directly on the `orders.status` transition.

**Fixed in `20260813000600_prepaid_dispatch_fix.sql`** (applied to production): both the trigger and `set_order_delivery()`'s `where` clause now treat `shipping_payment_method = 'prepaid_wallet'` as an alternative already-confirmed state — an order is dispatch-ready if *either* the automatic fee was charged *or* the manual negotiation was accepted. `actual_shipping_fee` and the `p_actual_fee` compatibility check now use `coalesce(proposed_shipping_fee, shipping_fee)` so they resolve correctly on the prepaid path too (`proposed_shipping_fee` stays null there; `shipping_fee` holds the real charged amount).

**Frontend also fixed** (was silently broken in the same way — worth knowing even though the RPC fix alone would have surfaced a clear error instead of nothing):
- `DeliveryModal.jsx` — `submit`'s guard, the header copy, and the fee shown/sent to the RPC all branch on a new `isPrepaid = order.shipping_payment_method === 'prepaid_wallet'` / `confirmedFee = order.proposed_shipping_fee ?? order.shipping_fee`, instead of assuming `proposed_shipping_fee` is always populated.
- `Merchant/Orders.jsx` — the order-detail "Shipping fee / dispatch" panel had exactly one branch, `!selectedOrder.shipping_fee_confirmation_status`, which is `true` for both "genuinely needs manual pricing" *and* "already prepaid automatically" (both leave that column null) — it was showing "enter the actual shipping fee for Reseller approval" on already-paid orders, with no way to reach "Enter delivery details" at all. Added a `shipping_payment_method === 'prepaid_wallet'` branch ahead of it showing the charged fee and the dispatch button directly. The list-view "Shipping fee" column badge got the same branch (new "Paid — ready to dispatch" badge) so it's visible without opening the detail view.
- `PurchaseHistory.jsx` (reseller side) — was already safe by construction (its branches only fire on non-null `shipping_fee_confirmation_status` values, so a prepaid order correctly fell through to `—`), but added a matching "Paid" badge for consistency/visibility rather than leaving it blank.

**Not done**: no live click-through — there's no real order in the `processing` status with `shipping_payment_method = 'prepaid_wallet'` yet in production (no merchant has pickup coordinates set except the unapplied test-account fix, so no real order has taken the automatic path yet). Verified via `npm run lint` (clean), `npm test` (45/45), and a clean `supabase db push` (a broken function body would have failed it). Whoever picks this up next should place one real test order end-to-end (merchant with a pickup pin + customer with a delivery pin) and click through Orders → dispatch to confirm live, not just trust the migration compiled.

### Gap 2 (real gap, discussed with owner but not yet built): no vehicle-type choice for the actual courier booking

The owner asked specifically about this (see chat: "paano kapag kotse ang gusto book ni merchant tapos motor lang ang nasa system... iba-iba ang shipping fee ng courier type ni Lalamove"). Investigated and confirmed:

- `supabase/functions/_shared/lalamove.ts:86-111` (`requestQuotation`) accepts an optional `serviceType` param but defaults to `'MOTORCYCLE'` (`:102`) if not given.
- `supabase/functions/_shared/delivery/adapters/lalamove.ts` (`getQuote`/`createBooking`) **never passes a `serviceType`** — every Lalamove quote/booking this system has ever requested, or will request, asks for a motorcycle, regardless of actual order size. This predates this session but is directly relevant to it.

There are three genuinely separate "vehicle" concepts in the system now, and only one is wired end-to-end:
1. **The automatic platform estimate** (Motorcycle/Sedan tier, this session's work) — determines what the *customer* is charged, fixed at order time, never revisited.
2. **The real courier vehicle the merchant needs** — a merchant decision, made when actually arranging delivery, that can legitimately differ from #1 (e.g. cart data undersells real bulk, or the merchant just prefers a bigger vehicle).
3. **Lalamove's own `serviceType`** — currently hardcoded to MOTORCYCLE with no way to request CAR/VAN/etc.

**Discussed recommendation** (also not yet built): keep #1 fixed as what the customer pays — no re-billing the customer if the merchant's real courier costs more, same as how Shopee/Lazada shipping estimates work. Add a vehicle-type selector to `DeliveryModal.jsx`/the "Get delivery quote" flow in `ShippingFeeModal.jsx` so the merchant can request a real Lalamove `serviceType` matching what they're actually shipping, threading that through the adapter and edge functions (`delivery-quote`, `delivery-book`) which currently have no `serviceType` parameter anywhere in their request bodies either. The cost difference is the merchant's own fulfillment cost, not something the customer sees again.
