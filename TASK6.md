**Most important finding — a live, currently-shipping bug, not just a gap:** campaign discounts are computed and displayed **client-side only** (`utils/campaigns.js` → `campaign_discount_percent` on the cart item → `utils/pricing.js`'s `getUnitPrice`). The actual money-moving RPC, `place_order()` (called via `place_receiver_shipping_order`/`place_customer_receiver_shipping_order`), recomputes `unit_price` from `product.price`/`wholesale_price` + `discount_tiers` only — it never reads `campaigns`, `merchant_campaigns`, or any campaign discount. **A shopper sees "20% OFF" in their cart and is charged full price at checkout.** A `product_unit_price()` SQL function exists that *does* include the campaign discount, but it is dead code — nothing calls it. This must be fixed as part of Phase 9 (Automatic Promotion Engine) at the latest, and is flagged as a candidate for an earlier, isolated hotfix given it's a real financial-trust bug independent of the rest of this project.

## Phase 10 — Voucher Engine (complete, deployed live)

Net-new module — Phase 1's grep of `voucher|promo_code|discount_code` across `src/` found zero matches, so this is genuinely additive, not an improvement of something existing.

**Built (migrations `20260806001800`–`20260806002200`):**
- `vouchers` (scope: `platform`/`merchant`/`product`/`category`/`shipping`; discount type `percent`/`fixed`; min spend, usage limit, per-user usage limit, max-discount cap, active window) and `voucher_redemptions` tables.
- `resolve_voucher()` — the single source of truth for whether a code is usable right now for a given buyer/merchant/cart, called by both `quote_order()` (preview) and `place_order()` (authoritative, re-validated at the moment of purchase so a code that expired or hit its limit between quote and place is caught, not silently honored). `validate_voucher()` is a thin auth.uid()-bound wrapper for direct client calls.
- `quote_order()`/`place_order()` extended with an optional `p_voucher_code` param (default `null`, so every existing caller keeps working unchanged) — same "server recomputes/re-validates everything" pattern already used for campaign pricing.
- Admin `Vouchers.jsx` (`/admin/vouchers`, new `vouchers` staff permission) — create/edit/enable-disable/delete any scope, including platform-wide and shipping.
- Merchant `Vouchers.jsx` (`/merchant/vouchers`) — create/edit/enable-disable/delete vouchers scoped to their own store/products/shipping (no platform option).
- `Reseller/Checkout.jsx` — voucher-code input + Apply/Remove, a discount line in the price breakdown, and the code passed through to the actual order-placement call.

**Security gap found and fixed before shipping the UI (not caused by any UI code — found while building on top of the already-deployed schema from a prior session):** the first voucher migration (`20260806001800`) granted `insert, update, delete` on `vouchers` directly to `authenticated`, with RLS only checking `created_by = auth.uid() or is_admin()`. That check never looks at the caller's *role* or the voucher's *scope*, so any authenticated reseller or customer could have inserted a row with `scope='platform'` and `created_by=themselves` — a live, redeemable, marketplace-wide discount voucher created by anyone. Closed in `20260806002100_voucher_write_rpcs.sql` by revoking the direct grants and adding `create_voucher()`/`update_voucher()`/`delete_voucher()` — security-definer RPCs that validate role and force `merchant_id` to the caller's own id for any non-admin caller (the client-supplied value is ignored, not just checked). Scope/code/merchant/product/category are immutable after creation by design — edit price/window/limits or deactivate and create a new voucher if the target itself needs to change, the same tradeoff already made for `campaigns`.

**Second gap found while wiring the checkout UI:** `Checkout.jsx` never calls `place_order()` directly — it calls `place_receiver_shipping_order()`/`place_customer_receiver_shipping_order()` (fixed-arity wrappers from `shipping_engine_migration.sql`) that hardcoded the call into `place_order()` with no voucher parameter at all. Without fixing this, a voucher would have shown correctly in the `quote_order()` price preview and then been silently dropped at the real money-moving step — the exact "shopper sees a discount, gets charged full price" bug class Phase 1/9 already found and fixed once for campaigns. Fixed in `20260806002200_voucher_checkout_wrapper_functions.sql` by adding an optional `p_voucher_code` param to both wrappers (dropped and recreated, not overloaded, so every existing caller keeps working).

**Live-verified via direct SQL against the deployed database** (this project's established methodology for backend-only verification, per Phase 1/2's own precedent — see below for what this did *not* cover):
1. Simulated a real, non-admin, non-merchant reseller account attempting `create_voucher(..., scope='platform', ...)` → correctly rejected with `FORBIDDEN`.
2. As the admin/merchant demo account, created a real `scope='product'` voucher on a live product ("Barako Drip Coffee 10-Pack"). Called `quote_order()` as the reseller test account with the code applied → correct wholesale subtotal, correct 10%-off discount amount, correct total.
3. Called `quote_order()` with a nonexistent code → `voucher_valid: false`, `voucher_error: 'VOUCHER_NOT_FOUND'`, full undiscounted subtotal charged instead — confirms an invalid code fails closed rather than open.
4. Simulated the same non-owner reseller attempting `update_voucher()` on the admin's voucher → correctly rejected with `FORBIDDEN`.
5. Inserted a redemption row against the test voucher, then attempted `delete_voucher()` → correctly rejected with `VOUCHER_HAS_REDEMPTIONS` (delete is meant to be blocked once a voucher has real usage; disable it instead).
6. Cleaned up the test voucher and redemption row afterward.

**Not verified — full browser checkout end-to-end (voucher input → Apply → Pay & Place Order) was not exercised**, and this is a real gap, not just a formality: attempting it hit an existing, unrelated `DEVICE_APPROVAL_REQUIRED` block on the deployed site (a stale/other-device session already occupying the only real login available in this environment) — correctly blocked by that security trigger rather than bypassed, same as the identical situation Phase 9 already ran into and correctly declined to work around. No OTP-authenticated browser session was available this session to complete a real Reseller checkout. **Recommend the project owner run one real checkout with a voucher code applied before fully trusting this in production** — same recommendation Phase 9 left for campaign checkout, still open for both.

## Note on "campaign performance view" (mentioned in Phase 2's spec, not yet built)

`order_items` has no `campaign_id` column today, so there's no exact way to attribute a past order to a specific campaign submission. A best-effort view (join `order_items` → `products` → `campaign_products`, filtered by the order's `created_at` falling inside the campaign's date range) would be approximate and could misattribute orders placed on a product that happens to also be in another campaign at the same time. Recommend building the real version once Phase 9 (checkout) is wired to campaign pricing — at that point `place_order()` can stamp the actual `campaign_id` onto each `order_item` at the moment of sale, giving exact attribution for free.
